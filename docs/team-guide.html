01원본의 문제 원본

  • Universe가 god 클래스이자 Singleton: 보드 생성, 그리기, 마우스, 메뉴, 시계 구독, 파일, System.exit까지 모두 담당. 클래스가 처음 쓰일 때 자기를 만들고, 그 과정에서 메뉴와 시계까지 만들어서 창 없이는 모델을 테스트할 수 없음
  • Cell에 시뮬레이션·그리기·클릭·저장이 섞임: 계산만 하는 셀도 java.awt에 의존
  • 두 스레드가 같은 보드를 만짐: 계산은 java.util.Timer 스레드에서, 클릭과 그리기는 EDT에서 실행. 이를 막는 static 잠금에 동기화가 없음
  • 버그: transition() 반환값이 반대라 블록 건너뛰기 최적화가 꺼져 있음, 불러온 셀이 활성 표시를 안 해서 틀리게 진화, 저장 시 좌표를 두 번 기록

원본의 한 틱

  • 계산은 Timer 스레드, 그리기와 클릭은 EDT에서 실행
  • 계산 도중에 클릭이 끼어들면 셀 상태가 덮어써짐

02바뀐 구조 core에서 구현

  • 모델과 화면 분리 (MVC): 모델(com.holub.life.model)은 Swing, 메뉴, 시계, 파일을 모름. 패키지로 강제
  • 모델의 입구는 LifeModel 하나 (Facade): Composite(Neighborhood, Resident)는 package-private로 숨김
  • Singleton 제거: Life가 객체를 new로 만들어 넘겨줌. 테스트에서 LifeModel.builder().build() 한 줄로 보드 생성
  • 모두 EDT 한 스레드: 시계를 javax.swing.Timer로 바꿔 틱·클릭·그리기가 차례로 실행. 잠금 삭제
  • 원본 기능 유지: 바뀐 블록만 계산(반환값 수정으로 복구), 바뀐 셀만 다시 그리기, 활성 블록 파란 테두리, 원본 .life 파일 읽기
  • 검증: JUnit 52개, 실제 창 자동 점검 15개 통과
  • 그림의 색 점선 테두리와 글자: 그 부분의 담당자
  • 위쪽 상자들은 원본 동작을 유지하는 최소 형태만 있음. 최종 설계는 담당자가 정함

03담당자별 할 일

  • 정리 순서: 원본 문제 → core의 1차 결정 → 대안 비교 → 선택과 근거
  • core의 결정을 그대로 써도 됨. 단, 대안과 비교한 근거(테스트, scripts/bench.sh 수치, 변경 범위) 필요
  • 대안 후보는 출발점일 뿐. 다른 방식이나 직접 찾은 문제도 좋음

A규칙·경계·계산 내부 (core)

  • 원본 문제: 생존 규칙 B3/S23 하드코딩, 경계가 죽은 셀로 고정, transition() 반환값 반대, 호출자가 계산 → 적용 순서를 지켜야 함, Direction의 LSP 위반·가변 상태 노출
  • core가 바꾼 것: Rule Strategy(B/S 표기), Boundary enum(DEAD / TORUS), transition() 반환값 수정, step()이 순서를 숨김, Direction 불변 값 객체, 보드 크기 지정
  • 대안 후보: Boundary를 인터페이스나 Decorator로 / Rule을 람다로 / Composite 대신 평평한 배열 + 바뀐 셀 집합
  • 고민할 것:
    • Boundary를 인터페이스로 만들면 package-private인 Cell이 public 시그니처에 드러남. 이걸 피할 방법이 있는지
    • Composite 블록 최적화의 값어치: 셀이 드문 보드에서는 이득이 크고, 30% 무작위 보드에서는 거의 없음
    • 계산이 원본보다 10~15% 느림. 원인은 알림에 담는 바뀐 셀 목록 비용
  • 남은 결함:
    • 설계: 원본 주석이 Flyweight라는 이름을 잘못 씀 (문서에 기록)

B저장과 되돌리기

  • 원본 문제: 저장 형식이 Neighborhood 안의 Java 직렬화로 고정, 좌표를 두 번 기록, 불러온 셀이 활성 표시를 안 함, 오류를 Universe가 JOptionPane으로 직접 표시
  • core가 바꾼 것:
    • 3계층: BoardSnapshot(불변, 크기 + 산 셀 좌표) ← BoardSerializer(형식) ← BoardFileIO(확장자로 형식 선택, 파일 열고 닫기)
    • LifeModel.snapshot() / restore(). 두 번 기록·불러오기 활성 표시 문제 해결
    • 원본 .life 파일 호환 형식 하나(JavaSerializationFormat)
    • 편집 단위 BoardEdit (여러 셀을 한 번에 바꾸고 알림은 한 번)
  • 대안 후보: GoF Memento(바깥에서 내용을 못 봄) vs 지금의 공개 Snapshot / 형식 선택을 확장자 맵, Factory, 파일 내용 감지 중 무엇으로
  • 고민할 것:
    • 스냅샷에 규칙·경계까지 넣을지 (지금은 보드 상태만)
    • 저장·불러오기 오류를 어디서 사용자에게 보여 줄지
  • 남은 결함:
    • 설계: 저장·불러오기 오류를 Life.installGridMenu가 JOptionPane으로 직접 표시 (원본 코드를 그대로 옮긴 상태)

C스레드와 시계

  • 원본 문제: Timer 스레드와 EDT가 같은 보드를 만짐, static 잠금에 동기화가 없음, Clock Singleton, 생성자가 메뉴를 만듦, 속도를 메뉴 이름 첫 글자로 고름
  • core가 바꾼 것: javax.swing.Timer로 틱을 EDT에서 실행, 잠금 삭제, Singleton 제거, 메뉴 코드를 ClockMenu로 그대로 옮김(첫 글자 분기는 그대로 남김)
  • 대안 후보: 계산 스레드 + 불변 스냅샷 전달(이중 버퍼) / Active Object / 잠금으로 동기화 / 시계는 틱만 알리고 보드가 구독
  • 고민할 것:
    • EDT 하나로 충분한지: 64×64는 한 틱 0.4ms, 1024×1024에 셀 30%면 53ms로 Fast 간격(30ms)을 넘음
    • 리스너를 어느 스레드가 부를지 (D와 함께 결정)
  • 남은 결함:
    • 설계: 속도를 메뉴 이름 첫 글자로 고름 (이름을 바꾸면 깨짐)
    • 설계: 시계 메뉴 설치가 ClockMenu의 static 메서드에 있음 (생성자에서 떼어 내기만 함)
    • 설계: Publisher 설계 검토 안 됨
    • 기능: 메뉴가 열려 있으면 갱신을 멈추는 원본 1.02 우회 코드가 EDT로 바꾼 뒤에도 필요한지 확인 안 됨

D모델 입구와 화면

  • 원본 문제: Universe god 클래스, 셀이 스스로 그리고 클릭을 받아 모델이 java.awt에 의존, Composite가 public으로 다 드러남
  • core가 바꾼 것:
    • LifeModel Facade, 읽기 전용 BoardView(보드를 읽기만 하는 코드용)
    • BoardListener 알림 세 가지(stepped, edited, reset)에 세대와 바뀐 셀을 담음
    • UniversePanel이 바뀐 셀만 다시 칠하고 활성 블록 파란 테두리를 그림(원본 redraw 최적화 유지)
  • 대안 후보: 읽기 전용 Proxy / 틱마다 불변 스냅샷을 화면에 넘기기 / 원본처럼 객체가 스스로 그리기 / 알림을 push 대신 pull로 / MVVM
  • 고민할 것:
    • 리스너를 어느 스레드가 부를지 (C와 함께 결정)
    • 구조를 바꿔도 바뀐 곳만 그리기가 깨지지 않게 (UniversePanelTest 픽셀 비교 테스트가 확인)
  • 남은 결함:
    • 기능: 보드가 화면보다 크면 실패 (원본 주석). 지금은 셀 크기를 최소 1픽셀로 막아 둠

E생성과 조립

  • 원본 문제: Universe·Clock Singleton과 생성 사슬로 창 없이 테스트 불가, MenuSite static Singleton, MenuSite.establish를 반드시 먼저 불러야 함, System.exit가 Universe 안에 있음
  • core가 바꾼 것: Singleton 제거, Life가 new로 조립(composition root), LifeModel.builder()(크기·규칙·경계), copy()(같은 설정의 새 보드)
  • 대안 후보: Abstract Factory / Service Locator / 설정 객체 / Singleton에 reset을 붙이는 방식 / 모듈별 install(...)
  • 고민할 것:
    • 모듈이 늘어도 Life에 한 줄씩만 추가되는 구조
    • 메뉴 명령(Clear·Load·Store·Exit)의 구조. 지금은 Life 안의 평범한 ActionListener
  • 남은 결함:
    • 설계: MenuSite가 static Singleton (전역 상태, 테스트 불가)
    • 설계: MenuSite.establish를 반드시 먼저 불러야 함 (생성 순서 의존)
    • 설계: System.exit가 Life.installGridMenu 안에 있음

  • 같이 쓰는 파일 (병합 주의): 기능은 안 겹쳐도 여러 명이 함께 쓰는 파일. 병합 전에 main을 받아 다른 사람 변경을 확인하고, 병합 후 빌드·테스트 확인

    • MenuSite: E가 고치지만 Life(B·E)와 ClockMenu(C)가 MenuSite.addLine을 씀. 사용 방식이 바뀌면 줄이 안 겹쳐도 git 충돌 없이 빌드가 깨짐. E는 메뉴 등록 방식을 먼저 정해 병합하고 알리기
